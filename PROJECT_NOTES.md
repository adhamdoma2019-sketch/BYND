# Shop platform (first client: BYND) — project notes

Keep this file up to date. At the end of every work session the assistant should update the
CHANGELOG and any section that changed, and give the owner the new file.

## 1. What it is
A multi-tenant online shop + small back office. BYND (sports/lifestyle brand, Egypt) is the first
shop; the platform must stay general (nothing hard-coded per shop). Languages: English + Arabic
(full RTL). Payment: cash on delivery only for now. Free plans only until real sales.
BYND's first products: hexagonal medal displays in several colors (photo changes per color) and a
"My Running PRs" board (standard board + distance plate 10 km / half marathon / marathon; extension
plates can also be bought alone). Reference brand the team likes: medalrise.com (inspiration only).

## 2. The owner
No coding background. Slow, step by step, plain language, exact clicks. Explain decisions
(what / why / alternatives / impact). Never ask for passwords, keys or tokens.
Cannot open a browser from the assistant side: ask for screenshots for anything visual.

## 5. Data model (Firestore)
- `tenants/{slug}`: PUBLIC shop record: name{en,ar}, slug, ownerUid, isActive, theme{accent}, appearance{mode,font,radius,announcement{enabled,text,link,more[]}} (up to 4 top-bar messages in total),
  brand{logoUrl,logoDarkUrl}, hero{slides,intervalSeconds,fade,autoplay,textStyle card|plain}, highlights[{title{en,ar},text{en,ar}}] (max 4), pages{about|privacy|returns|shipping|terms:{body{en,ar}}}, checkout{fields,customFields,promoOnQuantityPrices (default true: promo codes also apply to quantity-priced items)}, shipping{zones}, contact{...}, defaultCountryCode, orderPrefix.
  Sub-collections: `auditLogs` (who changed what) and `stockMovements` (every stock change; counted products add optionChanges[{key,label,delta,after}]) — add-only.
- `users/{uid}`: tenantId, role owner|manager|staff, name, email, active. Created at signup (owner) or by /api/team.
- `products`: tenantId, name/description {en,ar}, price, stock, sku, imageUrl, images[], isActive, deleted, isPreorder, preorderStyle preorder|madeToOrder (wording only), backorder (true = "stock first, then made to order"), countedOptions[] (ids of up to 2 colour/choice options that count their own stock), optionStock{"optionId.valueId": n} (public; only changed by orders, Add stock, Adjust, cancel/return; when countedOptions is set, `stock` = the SMALLEST of the per-option totals, kept in step by every one of those writers), comingSoon (visible, not orderable; the server refuses it), preorderMessage,
  priceTiers[{minQty,price}] (quantity prices: "from X pieces each costs Y", only valid steps kept, max 6), tierGroupOption (update 25: id of ONE colour/choice option; '' = the steps count all pieces of the product together, else pieces are counted separately for each choice of that option), wallDesigner (update 27: true = the product page shows the wall designer instead of the quantity box), packageQty / packagePrice (update 31: package price "every packageQty pieces cost packagePrice"; 0 / 0 = none; used INSTEAD of priceTiers, the counting follows tierGroupOption), minQty / maxQty (optional limits per order for the whole product, 0 = none), shippingExtra, relatedIds[], options[] (max 10; color / choice / addon (optionally asks for text) / text; values can have priceDelta and imageUrl; update 26: an option can have showWhen{optionId,valueId} = shown only when that colour/choice option ABOVE it has that value; update 35: a text option (or a tick box that asks for a word) can have overlay{enabled,y,size,color,bold} = its typed words are drawn ON the big product picture: y = % from the top (0-100, default 50), size = % of the picture width (2-30, default 8), color = #rrggbb (default gold #d4af37, white allowed), bold).
- `productCosts/{productId}` PRIVATE (owner/manager): costPrice, optionCosts{"optionId.valueId": cost}.
- `orders` (server-created only): orderNumber/Label (BYND-1001...), orderType normal|preorder, customer{...}, customFields[], items[] (lineTotal + packageSize only on lines of a package-price product: lineTotal = the EXACT amount of the line, unitPrice = lineTotal / quantity for display only, packageSize = pieces of the package when a full package applied; wallId when the line is a colour of a planned wall; name snapshot,
  unitPrice, unitCost, options snapshot, imageUrl, isPreorder, backorder (line made to order because stock ran out), stockKeys[] (which counted numbers the line took units from), tierMinQty (only when a quantity price applied: the "from X pieces" step used)), walls[] (update 29, only when the customer planned a wall: {id, productId, productName{en,ar}, count, cells[{q,r,c,h}], colors[{id,label{en,ar},color,count}]}; built by the server from the product), subtotal, discount, promo, shipping{zoneId,zoneName,fee}, shippingFee, totalAmount, status, statusHistory[].
- - `couriers` (owner/manager only): tenantId, name, kind company|own, collectsCash, defaultFee ("other areas"), fees{zoneId: fee}, returnFeePercent (default 100), active. Never deleted, only switched off.
- `courierSettlements` (owner/manager, ADD-ONLY ledger): tenantId, courierId, courierName, amount (signed: + courier gave cash to the shop, - the shop paid the courier), date, note, createdByUid. Mistakes are fixed with an opposite entry.
- `orders.courier` (written by the browser, owner/manager): snapshot { id, name, kind, collectsCash, fee, returnFeePercent, assignedAt }; null = none. Later changes to a courier never rewrite old orders.
- `expenses`, `promoCodes/{tenantId__CODE}`, `tenantPrivate/{tenantId}` (Telegram chat; owner only), `counters` + `rateLimits` + `orderTokens/{tenantId__hash}` (server only; update 38: one-time order code -> orderId, `expireAt` = 30 days; no rule block needed because Firestore refuses everything without a rule and only the server (admin key) touches it).
Queries use only equality filters (+ `orderBy` only on single fields in sub-collections) so no composite indexes are needed.

## 6. Rules that must not be broken
1. Money is computed ONLY on the server: /api/create-order and /api/quote use api/_lib/pricing.js + options.js + fields.js.
   The browser (src/utils/productOptions.js, checkoutFields.js) mirrors the rules for display; tests compare both.
2. Stock changes in one place each: sale (server transaction, writes a history line), Add stock / Adjust (client transaction), cancel/return (client transaction),
   new product (initial line). The product edit form never writes stock, with ONE exception: when a product counts stock per option, saving the product recalculates `stock` from optionStock inside a transaction (a colour may have been added/removed) and writes a history line if it changed. In a Firestore client transaction ALL reads must come before writes.
3. Roles: owner (several allowed) = everything; manager = all but team + shop settings; staff = orders only (cannot see costs, cannot cancel/return).
   Enforced in firestore.rules and hidden in screens (src/utils/roles.js). Rules are NOT emulator-tested. Update 37: staff on an ORDER (rules function staffMayUpdateOrder): only (a) fix customer name/phone/address/notes and/or (b) move the status exactly ONE step forward (pending>confirmed>processing>shipped>delivered, rules function nextOrderStatus must equal STATUS_FLOW in src/utils/orderRules.js, a test compares them) with exactly ONE new statusHistory line naming that status; staff cannot cancel/return, go back, skip, or touch anything else. Owner/manager unchanged.
4. Statuses: pending > confirmed > processing > shipped > delivered; cancelled; returned (from shipped/delivered, optional restock).
   Revenue = delivered orders only; COGS comes from the cost snapshot in each order; Net = Gross - expenses.
5. Order alerts: Telegram (free). WhatsApp automation would need the paid official API.
6. Spam: per-phone (5/day) and per-connection (40/hour) limits stored hashed in `rateLimits` (fails open), hidden trap field; promo guessing limited.
7. Look: light/dark/auto + any accent color with guaranteed readable text (src/utils/theme.js, tested), fonts, corners; storefront colors are CSS variables, never hard-coded.
8. Texts: add to BOTH languages; use logical CSS (ms-/me-/start/end) for RTL. Settings the shop controls live in its tenant record.

9. "Coming soon" products are refused by the server (placeOrder + quote), not only hidden in the screen. Shop text pages (privacy etc.) are shown as plain text, never as HTML.
10. Nothing is invented for a shop: highlights, text pages and top-bar messages show only what the shop wrote (no fake ratings/reviews).
11. Phone + email checks live in api/_lib/contactChecks.js (server = real gate) and src/utils/contactChecks.js (browser copy, a test fails if they differ). Egyptian shops (defaultCountryCode 20): mobile only (010/011/012/015), any spelling incl. +20 / 0020 / Arabic digits, SAVED as 01XXXXXXXXX; other countries: simple 7-30 chars check, saved as typed. Email = shape only (saved lower-case) + "did you mean gmail.com?" hints that never block.
13. Stock per option (update 18): a product sells in one of three ways: count stock, made to order (isPreorder, no counting), or stock first then made to order (backorder). Counting can be per option: each counted option's values have their own number, one order line takes one unit from EACH counted option (colour AND plate), the customer must choose every counted option, a sold-out value is refused by the server (or the line becomes made to order when backorder). Server rule = api/_lib/placeOrder.js (lines of one product share the numbers in order); browser mirror = src/utils/optionStock.js. Cancel/return give units back to the keys stored on the line (old lines without stockKeys are not given back on counted products).

Quantity prices (update 19): the price of one piece depends on the TOTAL of that product in the order (all colours/choices together): normal price, or the highest step whose "from" quantity is reached; extras of choices (priceDelta) are added on top per piece; cost per piece is unchanged. Min/max per order also look at the total. Server rule = api/_lib/placeOrder.js + quote.js (checkTotalQty, tierFor); browser mirror = src/utils/quantityPrices.js (identical copy, test checks) + cartPricing.js (cart prices every line from the whole cart). Update 25: with `tierGroupOption` set, the step looks only at the pieces with the SAME choice in that option (3 black + 3 blue: both lines get the step; 2 black + 1 blue: none); lines of the same choice with different extras still count together; the min/max per order and the 500 limit still look at ALL pieces; helpers tierGroupOption / groupKeyOf / groupQuantities live in the identical quantityPrices copies, the server uses them in placeOrder + quote, the browser in cartPricing (cart lines keep `tierGroup` from the moment they were added) + ProductPage (price table says "3+ pieces of the same colour"); productFields keeps the setting only when there are steps and the option really is a colour/choice list. Safety limit 500 pieces of one product per order (was 20); counted stock still limits. Promo codes: shop setting checkout.promoOnQuantityPrices; when off, the discount base excludes quantity-priced lines (pricing.js), the code's minimum order still uses the whole subtotal, and a code with nothing eligible gets PROMO_NOT_ON_QTY.

Couriers (update 20): delivered order -> courier earns `fee`, and holds the order total if collectsCash; returned -> fee x returnFeePercent/100, no cash; cancelled/open -> nothing. balance = cash - fees - handovers (+ courier owes the shop, - the shop owes the courier). Courier fees are subtracted in profit.js (calcProfit.courierFeesTotal) in the month of delivery/return, so do NOT also log the same delivery cost as a "Shipping" expense. Only owner/manager see or assign couriers (src/utils/couriers.js, roles.js canManageCouriers). Courier fees are NOT computed on the server (they are a back-office matter, not a customer price).

Package price (update 31): a product with `packageQty` N (2-500, whole) and `packagePrice` P (must be LOWER than N x normal price, else ignored) sells every full group of N pieces for exactly P; pieces that do not fill a package cost the normal price (+ the extras of choices per piece, unchanged). Example (BYND hexagon): normal 200, 3 for 500 -> 1 = 200, 2 = 400, 3 = 500, 4 = 700, 5 = 900, 6 = 1000. A product uses a package price OR price steps (productFields drops the steps when a valid package exists; the server ignores the steps too). Counting uses the SAME setting as quantity prices (tierGroupOption): a colour/choice option = the package needs N pieces of the SAME colour (3 black + 3 blue = 2 packages; 2 black + 1 blue = none), '' = any N pieces; BYND can switch the policy in the product form (Quantity prices > How are pieces counted) with no code change. EXACT MONEY: the group total is split between the lines of the group by cumulative rounding (packageAddition in the identical quantityPrices copies) so the lines always add up to the group total (3 for 500 is 500.00, never 500.01); every line of a package product carries `lineTotal`; money is added up with lineAmount / lineMoney (lineTotal when present, else unitPrice x quantity) in api/_lib/pricing.js computeTotals, cartPricing.js, CartContext, Checkout, wallGroups. Server = api/_lib/placeOrder.js + quote.js (cleanPackage, packageAddition); browser mirror = src/utils/quantityPrices.js + cartPricing.js (priceCartLines, packageHintFor; cart lines keep `pkg` {qty,price} and `tierGroup` from the moment they were added) + wallColors.js wallLines (pieces already in the cart count) + ProductPage (package box: 'Any 3 pieces of the same colour for 500', saving, live total, 'add N more' hint, per-colour hints on a coloured wall) + CartDrawer ('Package price' tag, hint).
